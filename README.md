# mini-redis

Krafton Jungle SW-AI 13기 · Week 11–12 「AI 함께하기」 미니 레디스

자주 조회하는 데이터(예: API 요청마다 확인하는 토큰)를 DB 대신 메모리에 캐싱하는 HTTP 서버입니다.

## 팀

**팀원**: 이서연, 이정욱, 조은

### 1. 목표

- **과제 목표**: 해시 테이블 기반 키-값 저장소를 직접 만들고, 외부에서 사용할 수 있게 한다.
- **우리 목표**: API 요청마다 반복되는 토큰 조회를 DB 대신 인메모리 캐시에서 처리해 DB 부하를 줄인다.

### 2. 진행 방식

- **유저 스토리 하나로 시작**: "백엔드 개발자로서, 요청마다 토큰을 확인하느라 DB가 바빠지지 않도록 자주 조회하는 데이터를 DB에서 매번 가져오지 않기를 원한다."
- **최소 단위로 쪼개서 개발**: 전체를 한 번에 설계하지 않고 단위 하나를 정하고 → 개발하고 → 다음 단위로 넘어갔습니다. (Store의 SET/GET → TTL → commands → HTTP → 클라이언트)
- **결정은 사람이**: 설계 질문마다 AI(Claude Code)가 선택지와 트레이드오프를 정리하고, 결정은 팀이 직접 내렸습니다.
- **실제 Redis를 정답지로**: 동작이 애매하면 redis-cli로 같은 상황을 실행해 보고 "진짜는 이렇게 하네, 우리도 이렇게 할까?"를 정했습니다.

## 프로젝트

### 1. 프로젝트 구조

```text
mini-redis/
├─ src/
│  ├─ server/     # 받기: HTTP 연결, body 읽기(1MB 제한), 응답 쓰기
│  ├─ protocol/   # 해석하기: 라우팅, 입력 검증, Reply → HTTP 응답 변환
│  ├─ commands/   # 실행하기: SET, GET, DEL, EXPIRE (명령 하나 = 파일 하나)
│  ├─ store/      # 저장하기: Map 기반 저장소, TTL 만료 판단
│  ├─ client/     # 쓰기: 서버 밖에서 쓰는 HTTP 클라이언트 라이브러리
│  ├─ types.ts    # 계층 공통 타입
│  └─ index.ts    # 서버 시작점
├─ test/          # 명령별·계층별 테스트 (node --test)
├─ examples/      # 캐시를 직접 써 본 실습 파일
└─ think-list.md  # 범위에서 제외한 한계 목록
```

요청은 한 방향으로만 흐릅니다.

```text
HTTP 요청 → server/ → protocol/ → commands/ → store/
                                               └─ Map<string, Entry>  ← 실제 데이터는 여기에만 있음
```

| 계층 | 책임 |
| --- | --- |
| server | HTTP 연결을 열고, body를 다 읽은 뒤 protocol에 넘기고, 결과를 응답으로 씁니다. |
| protocol | 주소로 명령을 찾고 입력을 검증합니다. 명령 결과(Reply)를 `{ "result": ... }` 또는 에러 응답으로 바꿉니다. |
| commands | NX 같은 명령 옵션을 처리합니다. 검증된 입력만 받기 때문에 에러를 만들지 않습니다. |
| store | 데이터를 저장하고, "만료된 키는 존재하지 않는다"는 규칙을 지킵니다. |

### 2. 개발 언어 선택 이유

**Node.js (TypeScript)** 를 선택했습니다. 빌드 도구 없이 Node.js 24에서 `.ts` 파일을 바로 실행합니다.

| 언어 | 동시성 구조 | 특징 |
| --- | --- | --- |
| **Node.js (JS)** | 싱글 스레드 이벤트 루프 | 실제 Redis와 구조가 같아서 락 없이도 안전하다. 1주차 미니 리액트와 같은 언어다. |
| Java (Spring) | 요청마다 스레드 | 락이나 `ConcurrentHashMap`이 꼭 필요하다. 대신 2주차 DBMS의 스레드 풀과 연결해서 설명하기 좋다. |
| C | 직접 선택 | 실제 Redis와 가장 비슷하지만, 일주일 안에 하기엔 부담이 크다. |
| Python | GIL 때문에 사실상 한 번에 하나씩 실행 | 빠르게 만들기 좋지만, 동시성을 설명하기는 애매하다. |

- **Redis와 같은 실행 구조**: 명령을 한 번에 하나씩 처리하는 싱글 스레드라서, 락 없이 명령 단위 원자성을 얻을 수 있습니다.
- **통신은 단순하게**: HTTP가 Node에 기본 내장이라 통신 코드에 시간을 거의 쓰지 않고, 저장·만료 설계에 집중할 수 있었습니다.
- **언어 통일**: 캐시 서버와 캐시를 써 보는 쪽(백엔드 코드)을 모두 Node.js로 맞춰서 오가며 헷갈릴 일을 줄였습니다.

### 3. 주요 개념

#### 인메모리 (In-Memory)

- 모든 데이터를 디스크가 아니라 메인 메모리(RAM)에 저장합니다.
- 디스크 I/O가 없어서 명령 하나가 아주 짧게 끝납니다. 그래서 싱글 스레드로 한 번에 하나씩 처리해도 충분히 빠릅니다.
- 대신 서버를 재시작하면 데이터가 사라집니다. 영속성은 이번 범위에서 제외했습니다.

#### 캐시 (Cache)

- 자주 읽는 데이터를 DB보다 빠른 곳에 잠시 보관해 두는 저장소입니다.
- 우리 서버는 **cache-aside** 방식으로 쓰는 것을 전제로 합니다. 앱이 먼저 캐시에서 GET하고, 없으면 DB에서 읽은 뒤 캐시에 SET합니다.
- DB 값과 캐시 값이 달라지는 문제는 **TTL(만료 시간)** 로 해결합니다. 오래된 값이 남아 있는 시간을 TTL로 제한합니다.

#### 왜 백엔드 안의 Map이 아니라 별도 캐시 서버인가

백엔드 프로세스 안에서 `Map`으로 캐싱하는 **로컬 캐시**가 더 빠르고 단순합니다. 별도 캐시 서버는 **여러 서버가 같은 캐시를 봐야 할 때** 필요해집니다.

| 로컬 캐시의 한계 | 상황 |
| --- | --- |
| 서버가 여러 대일 때 데이터 불일치 | 서버 A에서 로그아웃해 토큰을 지워도 서버 B의 캐시에는 남아 있어 계속 통과됩니다. |
| 캐시 중복 | 서버마다 같은 토큰을 각자 DB에서 가져와 각자 저장합니다. |
| 재시작·배포 시 캐시 소실 | 배포할 때마다 캐시가 비어서 직후에 DB로 요청이 몰립니다. |
| 다른 서비스와 공유 불가 | Node 서버의 Map은 다른 언어로 된 서비스가 읽을 수 없습니다. |

별도 캐시 서버는 모든 서버가 같은 원본을 보고, SET NX 같은 연산을 여러 서버가 동시에 써도 안전합니다. 대신 요청마다 네트워크를 한 번 거치는 비용이 생깁니다.

#### 싱글 스레드와 원자성

- 싱글 스레드가 보장하는 건 **동기 코드가 실행되는 동안에는 아무도 끼어들지 않는다**는 것까지입니다.
- `await`를 만나면 실행 흐름을 이벤트 루프에 넘기기 때문에, 스레드가 하나여도 그 틈에 다른 요청이 실행됩니다.
- 그래서 **명령 실행 경로(commands/, store/)에서는 `await`를 쓰지 않는다**는 규칙을 두었습니다. 명령 함수의 반환 타입을 `Promise<Reply>`가 아닌 `Reply`로 고정해서, 실수로 `async`를 붙이면 타입 검사에서 걸립니다.

```text
// await가 있으면 SET NX가 깨지는 예
요청 A: has("k") → false   (await로 양보)
요청 B: has("k") → false   ← A가 아직 set 안 함
요청 A: set("k", "a")
요청 B: set("k", "b")      → 둘 다 성공
```

#### TTL과 만료 처리

- 남은 시간이 아니라 **만료 시각**(`Date.now() + ttl`)을 저장합니다. 남은 시간은 계속 변하는 값이라 모든 키를 계속 갱신해야 하지만, 만료 시각은 조회할 때 현재 시각과 한 번만 비교하면 됩니다.
- 만료된 키는 **조회할 때 확인(lazy)** 해서 지웁니다. 클라이언트는 만료된 값을 받지 않습니다.

## 개발 회고

### AI만 믿으면 안 된다

설계 결정을 AI와 함께 정리하면서, AI가 적은 기록을 사람이 다시 확인해야 한다는 걸 두 번 겪었습니다.

1. **AI가 결정 내용을 잘못 옮겨 적음**
   - 규칙 문서(AGENTS.md)에 HTTP 형식을 `POST /set { "key", "value", "nx", "ttl" }`처럼 값 없이 적어 두었습니다.
   - 올바른 JSON이 아니라서 문자열 배열처럼 읽힐 수 있었습니다. 실제 값을 넣은 예시 `{ "key": "token", "value": "abc", "nx": true, "ttl": 1000 }`로 고쳤습니다.
2. **정하지 않은 것을 AI가 임의로 결정함**
   - DEL이 여러 키를 받을지는 "다음 라운드에서 정한다"고 미뤄 둔 상태였습니다.
   - 그런데 AI가 예시 모양만 보고 DEL 입력을 배열로 정하고, 코드와 테스트까지 여러 키 기준으로 작성했습니다.
   - 팀이 발견해서 키 하나만 받는 것으로 확정했고, 여러 키 삭제는 한계 목록(think-list.md)에 남겼습니다.

## Redis 개발 및 사용 후기

### 1. 후기

- 기능이 거의 없는데도 직접 만드는 건 생각보다 어려웠습니다. 진짜 Redis는 쓰기 정말 쉬웠는데, 그 쉬움 뒤에 정해야 할 것이 많다는 걸 알게 됐습니다.
- 우리 캐시를 직접 써 보며 막혔던 지점은 대부분 API 문제가 아니었습니다.

| 막혔던 지점 | 원인 |
| --- | --- |
| `60_000`이 무엇인지 | JS 숫자 구분자 문법. 익숙함의 문제 |
| NX를 붙였는데 효과가 안 보임 | cache-aside 흐름에서는 GET이 먼저 값을 돌려주면 SET까지 가지 않음. 개념의 문제 |
| 기대한 값 대신 다른 키의 값이 나옴 | 테스트 코드가 키 두 개를 섞어 씀. 코드 구성의 문제 |
| 저장 값에 `at`(현재 시각)을 왜 넣는지 | 매번 같은 값을 넣으면 NX가 성공했는지 거절됐는지 구분할 수 없음. 테스트 설계의 문제 |

- 직접 써 보면서 사용성 문제(클라이언트 라이브러리 없음, `null`이 여러 뜻)도 찾았습니다. 자세한 내용은 [유저 시나리오 문서](docs/user-scenario.md)에 있습니다.

### 2. 실제 Redis와 비교

| 항목 | 우리 mini-redis | 실제 Redis |
| --- | --- | --- |
| 저장 구조 | `Map<string, Entry>`, 값은 문자열만 | 자체 해시 테이블. 값마다 타입 태그가 붙어 여러 자료구조를 담음 |
| 명령 실행 | 싱글 스레드, 명령 경로에 `await` 금지 | 싱글 스레드 (6.0부터 네트워크 I/O만 멀티 스레드) |
| 통신 | HTTP, 명령별 주소 + 이름 붙은 JSON | TCP 위의 RESP 프로토콜. 명령은 문자열 배열 |
| 입력 검증 위치 | protocol 한 곳 | 각 명령 구현 안 |
| 에러 표현 | HTTP 상태 코드 + `{ "error": "..." }` | 에러도 응답 타입 중 하나 (`-ERR ...`) |
| 만료 방식 | lazy (키에 접근할 때 판단) | lazy + 주기적 샘플링 삭제(active) |
| TTL 저장 위치 | Entry 안의 `expiresAt` (절대 시각, ms) | 별도 `expires` 테이블에 절대 시각 (ms) |
| 만료 경계 | `now >= expiresAt`면 만료 | `now > expiresAt`일 때 만료 |
| TTL 단위 | ms | `EXPIRE`는 초, `PEXPIRE`는 ms |
| SET이 기존 TTL에 미치는 영향 | TTL 제거 | 같음 (`KEEPTTL` 옵션으로 유지 가능) |
| TTL이 걸린 키에 EXPIRE 다시 | 새 TTL로 덮어씀 | 기본은 같음 (7.0부터 NX/XX/GT/LT 조건 옵션) |
| EXPIRE에 0 이하 TTL | 400 에러 | 키를 즉시 삭제하고 `1` |
| GET 없는 키 | `null` | nil |
| SET NX인데 키가 이미 있음 | `null` | nil |
| EXPIRE 성공 | `"OK"` | 정수 `1` |
| EXPIRE 없는 키 | `null` | 정수 `0` |
| DEL | 키 하나, 지운 개수(`0` 또는 `1`) | 여러 키, 지운 개수 |
| 영속성·축출·트랜잭션 | 없음 ([think-list.md](think-list.md)) | RDB/AOF, maxmemory 정책, MULTI/EXEC와 Lua |
